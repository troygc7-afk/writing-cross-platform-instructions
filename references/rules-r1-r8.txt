==================================================
AGENT INSTRUCTION RULES — 跨平台指令撰寫與交付準則
版本：1.0
適用：任何要「寫指令給另一個 AI／另一個平台」的 Agent
==================================================

【適用時機】
當你要產出「給另一個 AI 執行的指令」時（例如：貼給 Copilot、貼給另一個 Agent、
貼給外部工具），在送出前必須逐條自檢本文件 R1–R8。任一條不通過，不得送出。

--------------------------------------------------
R1　先確認「對方手上有什麼」，再寫指令
--------------------------------------------------
條文：
在撰寫任何驗收／執行指令之前，必須先向使用者確認三件事，並取得明確答覆：
  (a) 被處理的內容（傳輸包／檔案，資料）是否已經在「同一個對話」中送出？
  (b) 該對話是否為全新對話，或延續既有對話？
  (c) 對方（另一個 AI）目前看得到什麼？
若使用者未答覆，必須在指令的第一段寫明「本指令假設 X 已存在；若不存在請停止並回報」，
不得默默假設。

為什麼：
「我以為它已經收到了」是跨平台指令失敗的第一大原因。對方看不到你以為它看得到的東西。

違反判定：
指令中出現「請驗證」「請檢查」等動詞，但全文沒有任何一句說明「被驗證物從何而來」→ 違反。

--------------------------------------------------
R2　驗收指令必須自帶 Step 0：前置條件檢查
--------------------------------------------------
條文：
任何驗收類指令，第一段必須是前置條件檢查，格式固定為：
  「如果你在目前這個對話中沒有看到 <具體特徵>，請立刻停止，只回報
   FINAL_STATUS: NOT_INSTALLED，並在缺失說明寫明『本對話未收到 <具體特徵>』。
   不要猜測、不要模擬、不要用一般常識補足。」
<具體特徵> 必須是可數、可比對的（例如：總行數、首行字串、末行字串、檔案數）。

為什麼：
沒有停止條件的指令，會讓對方用「合理推測」補足它沒收到的內容，產出看起來合理但虛假的結果。

違反判定：
指令中沒有「若未收到則停止」的分支 → 違反。

--------------------------------------------------
R3　對象名稱必須在第一段明寫，且與「被驗收物」一致
--------------------------------------------------
條文：
指令第一段必須同時寫出：
  (a) 被驗收的對象名稱（完整、可辨識）
  (b) 明確排除容易混淆的鄰近名稱，格式為：
      「請注意：被驗收的是 <A>，不是 <B>（<B> 是 <角色說明>，不在本次範圍）。」
  (c) 「若你找不到 <A>，請如實回報，不要改驗其他名稱。」

為什麼：
工具與產物、打包者與被打包物，名稱相近但角色完全不同。寫錯對象會讓整份測試失去意義，
而且對方不會主動告訴你「你問錯東西了」。

違反判定：
指令只寫「請驗證某 Skill」而未指明是哪一支，或未排除鄰近名稱 → 違反。

--------------------------------------------------
R4　禁止要求對方驗證「它沒有收到的東西」
--------------------------------------------------
條文：
指令中每一個「請檢查／請驗證／請確認」的對象，都必須在同一份指令內可追溯來源：
  - 若來源是「本對話稍早的訊息」，必須在指令中寫明是哪一則、有什麼特徵。
  - 若來源是「對方自己產生」，必須寫明它應該在何時產生。
  - 若來源不明，不得要求驗證。

為什麼：
要求對方驗證一個不存在的東西，只會得到 NOT_INSTALLED 或憑空編造的 PASS，
兩者都不帶任何資訊。

違反判定：
指令要求「檢查安裝狀態」，但全文沒有任何一句提供「可被安裝的東西」→ 違反。

--------------------------------------------------
R5　一則訊息只服務一個讀者
--------------------------------------------------
條文：
不得在同一則訊息中混合以下三種內容：
  (a) 給「使用者」的操作指示（請你貼給 X）
  (b) 給「另一個 AI」的指令本體
  (c) 給「使用者」的回覆判讀重點（要看它的第幾節）
若三者都需要，必須拆成三則訊息，或把 (b) 放進獨立檔案／獨立區塊並明確標示邊界。

為什麼：
混在一起時，使用者無法判斷「哪一段要複製、哪一段不用」。長度限制一切割，界線就消失。

違反判定：
同一則訊息中同時出現「請把下面整段貼給 X」與「貼上後請看它的第 N 節」→ 違反。

--------------------------------------------------
R6　要複製的長文，一律以「檔案」交付，不得用收合區塊
--------------------------------------------------
條文：
任何「使用者需要全選複製」的內容，若超過 20 行，必須：
  (a) 上傳為獨立純文字檔（.txt），提供可下載連結；且
  (b) 在訊息中只寫「請下載此檔，全選複製後貼上」，不把內容貼在訊息裡。
禁止使用「檢視／展開」收合區塊交付此類內容。

為什麼：
收合區塊在群組中無法可靠全選複製；且使用者無法確認內容是否完整、是否被截斷。
這正是「看不出哪一段要貼」問題的來源。

違反判定：
訊息中出現「N 行　檢視」這類收合容器，且該內容是要求使用者複製的 → 違反。

--------------------------------------------------
R7　明知會失敗的風險，必須「消除」而非「警告」
--------------------------------------------------
條文：
不得用「請不要只貼其中一段」「請注意長度」這類警告來代替解決方案。
若已知某操作有失敗風險（截斷、格式跑掉、複製不全），必須改採不會失敗的交付方式
（見 R6），而不是提醒使用者小心。

為什麼：
警告把責任推給使用者，卻沒有降低失敗率。使用者照做了還是失敗，等於沒解決。

違反判定：
指令中出現「不要只貼其中一段」「請完整貼上」等提醒，但未同時提供防截斷的交付方式 → 違反。

--------------------------------------------------
R8　驗收指令必須要求「可複核證據」，不得只要求「結論」
--------------------------------------------------
條文：
驗收指令必須逐項列出要求對方提供的證據，每項都要是「可被第三方獨立複核」的產出物，
例如：全文、雜湊值、逐項差異清單、實際執行輸出、完整 stdout。
並必須寫明：「沒有內容的『已驗證』不算證據。」
同時必須寫明判定鐵則：「任一項為 UNVERIFIED 即判定不成立，不接受『大部分通過』。」

為什麼：
「PASS」是一個結論，不是證據。只收結論的驗收，等於沒有驗收。

違反判定：
指令只要求對方回報 FINAL_STATUS 或「是否通過」，未要求具體產出物 → 違反。

--------------------------------------------------
【送出前自檢清單】（逐項打勾，任一未勾不得送出）
--------------------------------------------------
[ ] R1 已確認對方手上有什麼，或已在指令中寫明假設與停止條件
[ ] R2 指令第一段是前置條件檢查，含「未收到則停止」分支
[ ] R3 對象名稱已明寫，且已排除鄰近混淆名稱
[ ] R4 每個「請驗證」的對象都可追溯來源
[ ] R5 一則訊息只有一個讀者
[ ] R6 超過 20 行的可複製內容已改為檔案交付
[ ] R7 沒有用警告代替解決方案
[ ] R8 已列出可複核證據清單與 UNVERIFIED 鐵則

--------------------------------------------------
【違反後的處置】
--------------------------------------------------
1. 立即停止，不送出。
2. 在回覆中明寫「本指令違反 R<N>，已改為 <修正方式>」。
3. 若已送出並造成失敗，必須在下一則回覆中明確承認是哪一條違反，
   不得把責任歸給對方平台或使用者操作。
